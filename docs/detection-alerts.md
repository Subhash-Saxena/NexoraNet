## 1. Alert Lifecycle & State Machine

In enterprise Security Operations Centers (SOCs), alerts are managed through structured stages to ensure all anomalous behaviors are evaluated, tracked, and properly resolved.

NexoraNet implements this triage state machine:

```text
       +-----------------------+
       |          NEW          |  (Unreviewed alert generated by run)
       +-----------+-----------+
                   |
                   v
       +-----------------------+
       |     ACKNOWLEDGED      |  (Queued by analyst for inspection)
       +-----------+-----------+
                   |
                   v
       +-----------------------+
       |     INVESTIGATING     |  (Active inspection of packets/evidence)
       +-----+-----------+-----+
             |           |
             v           v
    +--------------+   +-------------------+
    |    CLOSED    |   |  FALSE_POSITIVE   |
    | (True Threat |   | (Benign/Expected  |
    |  or Remedi.) |   |   Traffic)        |
    +--------------+   +-------------------+
```

### Lifecycle States:
- **`NEW`**: Default state when an alert is created. Indicates that no analyst has reviewed the event yet.
- **`ACKNOWLEDGED`**: An analyst has assigned or queued the alert for examination.
- **`INVESTIGATING`**: The analyst is actively reviewing the packet capture, checking protocol headers, and executing investigation steps.
- **`CLOSED`**: The investigation has completed, confirming a genuine security policy violation, misconfiguration, or simulated attack.
- **`FALSE_POSITIVE`**: The investigation concluded that the flagged pattern was legitimate benign traffic (e.g. valid network diagnostic or failover).

Every status update records the transitioning user, timestamp, and optional justification reason into the `alert_status_history` audit log.

## 2. Alert Deduplication Strategy

High-volume network scans or bursts can trigger dozens or hundreds of individual rule match events. Generating a new alert for each matched packet causes severe **alert fatigue**.

NexoraNet uses a **deterministic windowed deduplication mechanism**:

$$\text{dedup\_key} = \text{rule\_id} : \text{source\_ip} : \text{destination\_ip} : \text{destination\_port} : \text{window\_bucket}$$

Where:
- $\text{window\_bucket} = \lfloor \frac{\text{first\_seen\_time}}{60.0} \rfloor$ (60-second rolling interval)

When an incoming packet match has an identical `dedup_key`:
1. It updates the existing alert record instead of creating a new one.
2. `packet_count` is incremented.
3. `last_seen_timestamp` is updated.
4. Additional packet evidence is appended to `alert_evidence`.

## 3. Dynamic Confidence Scoring

Confidence indicates the engine's certainty that the observed behavior represents the described phenomenon rather than sporadic network noise.

Confidence is computed dynamically into three tiers:

- **`HIGH`**: Strong statistical evidence or unambiguous protocol violation.
  - Examples: Conflicting MACs in ARP replies; 8+ consecutive SYNs without ACK; Shannon entropy $> 4.2$.
- **`MEDIUM`**: Clear pattern meeting threshold, but with possible benign overlap.
  - Examples: Periodic beaconing with small jitter; ICMP bursts.
- **`LOW`**: Borderline threshold match or limited sample size ($< 3$ events).

## 4. Evidence Binding Architecture

Every alert is linked to one or more `AlertEvidence` records:

- **`PACKET`**: Raw packet reference (`packet_number`, protocol, timestamp, 5-tuple, and JSON payload).
- **`FLOW`**: Aggregated flow summary (bytes, packets, flags).
- **`STATISTIC`**: Calculated metric (entropy, mean interval, standard deviation).
- **`DNS_QUERY`**: DNS query name, record type, response code, and entropy.
- **`TCP_FLAG`**: Specific sequence of TCP control bits (SYN, RST, FIN, ACK).
- **`ARP_ENTRY`**: MAC and IP binding pair.

Students can click **"Inspect"** on any evidence row in the UI to view the exact decoded protocol payload in JSON format.
