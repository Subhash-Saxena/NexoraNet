# NexoraNet Network Detection Engine

> **Tagline:** Learn. Simulate. Analyze. Defend.  
> **Phase:** Step 11 — Network Detection Engine  
> **Audience:** Students, SOC Analysts, Cybersecurity Beginners, Educators

---

## 1. Executive Summary

The **NexoraNet Network Detection Engine** is a deterministic, explainable, and educational detection system. It bridges the gap between passive packet inspection (Step 10) and hands-on Security Operations Center (SOC) analysis by evaluating network telemetry against rule-based signatures and statistical thresholds.

Students use the engine to observe how security monitoring systems identify suspicious or noteworthy patterns in network communications, understand the underlying protocol mechanics, inspect linked evidence, and conduct structured SOC alert triage.

## 2. Architectural Principles

1. **Deterministic & Explainable:** Every alert is generated by explicit, reproducible logic. No black-box machine learning or non-deterministic heuristics.
2. **Strictly Offline & Defensive:** The engine only evaluates static records in SQLite (parsed packet metadata from Step 10 or synthetic traces from Step 9). No raw packets are sniffed, transmitted, replayed, or executed.
3. **Neutral Educational Phrasing:** Alert titles, explanations, and investigation steps use objective technical terminology rather than sensational claims (e.g., *"Potentially noteworthy network pattern detected"* instead of *"Critical cyber attack underway"*).
4. **Concrete Evidence Binding:** Every alert links directly to the specific packets, flows, or statistical calculations that triggered it, allowing the student to inspect the raw artifacts.
5. **Interactive SOC Workflow:** Real-world SOC triage lifecycle (`NEW` → `ACKNOWLEDGED` → `INVESTIGATING` → `CLOSED` / `FALSE_POSITIVE`) with audit history tracking and analyst collaboration notes.

## 3. Data Flow & Normalization

The detection engine ingests parsed telemetry and structures it into three analytical layers:

### A. Normalized Event (`NormalizedEvent`)
Converts heterogeneous packet types into a standard structure with timestamps, 5-tuples (Source IP, Destination IP, Source Port, Destination Port, Transport Protocol), application-layer flags, and payloads.

### B. Flow Aggregation (`FlowAggregation`)
Aggregates directional communication pairs into coherent network conversations:
- Packet & byte counters
- TCP handshake states (`has_syn`, `has_syn_ack`, `has_ack`, `has_rst`, `has_fin`)
- Inter-arrival times (mean and standard deviation)
- Incomplete connection ratios

### C. Host Profile (`HostProfile`)
Builds per-IP state across the capture duration:
- Unique destinations contacted
- Unique destination ports queried
- Protocol distribution
- DNS NXDOMAIN error rates
- ARP MAC address associations

---

## 4. Deduplication & Confidence Scoring

To prevent alert fatigue and mimic enterprise SIEM/NDR systems:
- **Deduplication:** Repeated occurrences within a rolling time bucket (default 60 seconds) for the same rule, source IP, destination IP, and port are grouped into a single alert with an incremented `packet_count`.
  $$\text{dedup\_key} = \text{rule\_id} : \text{src\_ip} : \text{dst\_ip} : \text{dst\_port} : \text{time\_bucket}$$
- **Dynamic Confidence:** Alert confidence is calculated deterministically as `LOW`, `MEDIUM`, or `HIGH` based on sample size, failure ratio, and statistical deviations from baseline behavior.

---

## 5. Security & Isolation

- **No Code Execution:** Rule definitions use declarative JSON thresholds (`min_count`, `window_seconds`, `ports`) evaluated by safe Python routines. Dynamic `eval()`, `exec()`, or regex execution with unbounded backtracking are prohibited.
- **Data Protection:** All telemetry is confined to the local SQLite database (`nexoranet.db`). No telemetry is transmitted to third-party endpoints.
